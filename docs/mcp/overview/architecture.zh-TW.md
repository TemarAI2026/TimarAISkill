# MCP 架構說明

## 用途

本頁用於向外部接入方與 AI 編程助手解釋應如何理解 MCP。重點不是窮舉內部系統，而是把公開能力邊界說清楚，避免呼叫方自行發明額外層級或不被支援的執行期行為。

## MCP 的角色

MCP 是 Temar 平台統一的開放能力底座。

它在公開層面的職責包括：

- 提供單一一致的開放能力入口
- 統一執行期呼叫模型
- 統一簽名、請求識別、回應包裝語義與能力路由
- 為更上層的工具與協議適配層提供穩定的執行底座

## 與上層的關係

在目前架構裡：

- `skill` 是面向 AI 的引導與觸發層
- `x402` 是協議適配層
- 未來其他協議接入面，也應作為建立在 MCP 之上的適配層

這些上層入口若需要重用同一套收單、代付或公共簽名行為，就不應各自維護獨立業務核心，而應統一路由到 MCP。

## 第一階段由 MCP 負責的內容

在第一階段，MCP 負責以下公開能力面：

- 收單
- 代付
- 餘額
- 通知
- 公共執行期呼叫約定

這意味著，對外接入時應把 MCP 建模為「已發布資金相關開放能力的執行期 API 層」。

## 第一階段不由 MCP 負責的內容

MCP 目前不是以下內容的公開所有者：

- 商戶註冊流程
- KYB / KYC 處理流程本身
- wallet 內部實作細節
- settlement / ledger 內部實作
- 內部對帳流程
- 內部營運審批流程

這些內容要麼是執行期接入前的前置條件，要麼屬於目前公開 MCP 契約之外的平台內部能力。

## 給 AI 助手的建模規則

當 AI 編程助手閱讀這套文件時，應把 MCP 理解為：

- 已發布能力的呼叫入口
- 公共簽名與回應規則的落點
- 不是用來猜測 merchant、ledger、wallet 內部行為的地方

如果某個事實沒有出現在 MCP 文件或其指向的精確 reference 裡，就不應自行腦補。

## 推薦理解模型

規劃接入時，建議使用這套分層模型：

1. 業務准入與開戶發生在執行期之前
2. MCP 負責執行期能力呼叫
3. `skill` 負責提升 AI 助手理解與呼叫 MCP 的穩定性
4. `x402` 或未來其他協議層，負責把自己的接入面適配到 MCP

這樣做可以把公開接入邏輯集中在一處，降低人工客戶端、AI 生成客戶端與未來協議適配層之間的漂移。

## 常見錯誤

- 把 MCP 當成完整的商戶生命週期平台，而不是執行期能力層
- 在公開客戶端程式碼裡塞入內部 ledger 或 wallet 假設
- 讓每個上層適配面自己定義一套簽名與狀態語義
- 明明只是換接入面，卻在 MCP 之外重複維護收單或代付業務邏輯
