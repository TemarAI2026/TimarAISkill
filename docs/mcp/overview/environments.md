# 环境说明

## 用途

本页定义第一阶段 MCP 接入的运行时环境模型，目的是避免外部接入方和 AI 编程助手在不同环境之间混用凭证、混用假设、混用上线判断。

## 运行时模型

在运行时阶段，MCP 接入聚焦于少量动作：

- 选择环境
- 加载该环境对应的凭证
- 生成签名输入
- 调用已发布能力
- 在同一环境里核对返回状态和标识

环境切换属于运行时配置问题，不属于商户开户问题。

## 当前环境概念

当前公开文档默认至少存在这两类环境概念：

- `sandbox`
- `production`

实际 base URL、启用能力、发布时间窗和操作规则，应以正式平台配置和当前精确 reference 为准。

## 最小环境配置

每个环境都应被建模为独立配置集合，至少包括：

- base URL
- `apiKey`
- `secretKey`
- 请求超时策略
- 日志或追踪策略

不要在沙箱和生产之间共用一套凭证配置。

## 前置条件

在进入运行时环境接入前，应先完成：

- 商户注册
- 接入开通
- API 凭证签发

MCP 运行时文档不替代这些开户和准入步骤。

## 隔离规则

建议始终保持这些环境隔离规则：

- `apiKey` 和 `secretKey` 必须按环境分开管理
- 不要混用 sandbox 和 production 的请求参数
- 不要跨环境复用已保存的 `orderId`
- 不要因为某个能力在 sandbox 可用，就默认它在 production 也已开通
- 不要仅凭 sandbox 的状态行为就推断 production 一定一致，必须重新验证

## 上线前检查

在发布到 production 前，至少要在目标环境重新验证：

1. 签名行为
2. 必填请求头
3. 端点路径和方法
4. 状态处理与后续跟进逻辑
5. 异步通知或回调行为，如果有使用
6. 日志和追踪留存

## 常见错误

- 选对了环境，却用了另一套 `apiKey` / `secretKey`
- 用 sandbox 的 base URL 去打 production，或反过来
- 没有重查环境差异，就把客户端代码直接从测试推进到生产
- 把订单查询做成“无环境区分”的查找逻辑，导致跨环境误查
